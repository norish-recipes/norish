# 16: `RecipesContext` goes

**What to build:** `RecipesContext` leaves the shell. From there it read `library.list` and the pending imports on every page, though only the dashboard draws them. Every reader reads the plain hooks of `@norish/shared-react/recipes` instead: the list, the pending imports, favourites, deletes, and the imports that the avatar menu, the copied-link prompt and the search field start. Selection becomes a store. The context's subscriptions split by what draws their data: the import outcomes and their toasts stay in the shell, the list events and ratings mount on both Library pages, ratings mount on the recipe page, and calendar listens for recipe renames itself. The filters context stays in the shell until 17. Nothing visible changes. See `.scratch/app-structure/spec.md`, "Library (the third feature)" and the subscription rule under "shared-react".

**Blocked by:** None (recipes has landed)

**Status:** ready-for-agent

- [ ] First, before anything moves, three two-browser tests in `apps/web/__tests__/e2e/realtime/realtime.e2e.ts` pass against today's code: a housemate files the open recipe into a cookbook and the recipe page's cookbooks card shows it; a housemate's Pantry change reorders a Library sorted by pantry share; a housemate renames a recipe and an open calendar shows the new name. Each is checked with `--repeat-each`.
- [ ] The dashboard and the cookbook page read the list, the pending imports, favourites and deletes through the plain hooks, under the filters from the shell's filters context. The avatar menu's import modal, the copied-link prompt and the search field import through the plain mutations, with the same toasts.
- [ ] Selection is a global zustand store in `shared-react/recipes`. It holds each selected recipe's id, version and owner, the range anchor, and the actions the context had. Each Library page resets it on unmount, so a selection doesn't follow the reader into a cookbook. The delete animation and Escape-to-clear stay in web. The selection context and its own `recipes.onDeleted` subscription go, and the list events drop deleted ids from the store.
- [ ] The recipe events split. The import outcomes (`onImportStarted`, `onImported`, `onFailed`) mount once in the shell, with their toasts worded as before. The list events (`onCreated`, `onUpdated`, `onDeleted`, `onDeleteKept`, `onConverted`, `onRecipeBatchCreated`) and ratings mount through one hook that the dashboard and the cookbook page each call; 17 moves that call into library's root. The recipe page mounts ratings beside its recipe, shares and enrichment.
- [ ] The list events stop invalidating `calendar.listItems`. Calendar's context (`app/(app)/calendar/context.tsx`), which the calendar page and today's meals mount, invalidates it on `recipes.onUpdated` itself.
- [ ] `mobileSearchOpen` goes, since nothing sets it. `actionBarOpen` moves from `stores/useAppStore.ts` to `lib/`, and the store file goes.
- [ ] `createRecipesContext`, web's `RecipesContextProvider` and its binding are deleted, with the context's unread fields. The recipe toast adapter goes with them or moves beside the import outcomes it serves. Nothing in web or shared-react imports the recipes context.
- [ ] The selection store gets a unit test: a toggle, a range from the anchor, a reset, and a deleted id leaving it. `recipes-context-hydration.test.tsx` becomes a test of what replaced it, and the web tests that mocked `useRecipesContext` mock the plain hooks.
- [ ] Gates green: `pnpm lint`, `pnpm typecheck`, `pnpm test:run`, `pnpm i18n:check`, `pnpm build`, `pnpm format:check`, `pnpm deps:cycles`, and mobile's lint, typecheck, test and `expo export --platform ios`.
