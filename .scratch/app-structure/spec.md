# App structure: features over one shared-react

Status: ready-for-agent

Settled in `/grilling` sessions on 2026-11-07 (the architecture and the groceries pilot), 2026-11-09 (recipes, the second feature, and the decisions library takes with it) and 2026-11-10 (library, the third feature, which changed where subscriptions mount and where panels live). Target Version: 0.27.0-beta. Tickets are in `issues/`: 01–09 are the groundwork and the groceries pilot, 10–15 are recipes, 16–19 are library. Each later feature gets its tickets once the one before it has landed. Starts on a branch off `rc/0.27.0-beta`, which `feat/mobile-catch-up` has merged into (4589f4f95); every feature stays on `refactor/app-structure`, since it is one refactor.

## Problem Statement

Web and mobile are about to be built side by side again, and they are organised differently. Mobile's catch-up laid it out by feature; web is laid out by type at the top (`components/`, `hooks/`, `context/`, `stores/`) with domains inside, so one feature is spread across up to five folders. Groceries alone lives in `app/(app)/groceries`, `components/groceries`, `hooks/groceries` and shared-react's `contexts/groceries` and `hooks/groceries`.

The "heavy" contexts are mostly server data in disguise. `RecipesContext` (23 fields, mounted app-wide), `RecipeDetailContext` (~40), `AdminSettingsContext` (~50), `GroceriesContext`, `StoresContext` and `CalendarContext` each bundle TanStack Query data, mutation callbacks and a realtime subscription into one value, so a component that only needs `createRecipe` re-renders whenever the recipe list changes. Two layers (`WebUserContext`, the `RecipesContextAdapter`) only re-provide a value.

shared-react reaches both apps through 19 `create*Hooks({ useTRPC, … })` factories plus 10 context factories, and each app binds every one in its own files. Infer-mode React Compiler can't see factory-built hooks without a `"use memo"` directive, and aliasing them caused the hook-alias trap on mobile. What the factories inject is almost never another feature: it is `useTRPC`, reference data (units, recurrence config), the signed-in **Reader** (id, name, allergies, household) and platform adapters (toast, navigation, error, storage).

After the pilot, the recipe surfaces still carry all of it. The recipe page's context holds the recipe, its shares, ratings, favourites, enrichment, conversion and servings in one value, eight of its fields have no reader, and the page's pieces are spread over `app/(app)/recipes/[id]`, `components/recipes`, `components/recipe` and `components/shared`. The shared recipe page renders ten of those pieces from a route folder of its own with a second provider. The icons context renders every ingredient icon on a screen when one food joins it. And the shell keeps the Library's list, its subscriptions and the Pantry's mounted on every page, though only one screen draws each.

## Solution

Both apps are laid out the same way, and logic a feature shares lives once in shared-react under the same domain name.

- An app's `features/<feature>/` holds that feature's screens, components and platform hooks. Route files compose features; a feature never imports another, and a panel several features open lives in the shared folders.
- Server data is read through plain hooks over the Query cache, never copied into a context or a store. Whatever draws data mounts the subscriptions that keep it current: a feature's root for its screens, a panel for itself while it is open, and the shell for what it draws itself plus the Reader.
- Client state that several components share lives in a zustand store; state one component owns stays in `useState`. A store whose first value comes from the request or the page is made per page and handed down through a context that holds only the store.
- shared-react is organised by feature, creates the tRPC context once, and takes platform differences through one adapter. Its features don't import each other either; they import cross-cutting folders.

Groceries is the pilot, recipes the second feature and library the third. The rest follows in order, and the old type folders are deleted when the last feature has migrated.

## Implementation Decisions

### Features

- Features are named by domain: `library` (the dashboard's grid, filters and selection, and the cookbook page), `recipes` (detail, new, edit, and the shared recipe page), `groceries` (stores and pantry included), `calendar`, `imports`, `settings` and `auth`. Most map to one route; a route that shows several, like the dashboard with today's meals, composes them.
- The cookbook page is the **Library** scoped to one cookbook: it renders the same grid, card, selection, search, view toggle and filters panel as the dashboard, so it belongs to `library` rather than a feature of its own. A shared recipe is the recipe page for someone holding the link, and it renders the recipe page's read-only pieces, so it belongs to `recipes`.
- An app feature holds only the subfolders it needs. Code two or more features use lives in the app's shared `components/`, `hooks/` or `lib/`.
- Imports run one way: shared folders, then features, then routes. A `no-restricted-imports` override in each app's ESLint config enforces it, as mobile's already does.
- A panel opened by more than one feature lives in the shared `components/Panel/consumers/`: `MiniGroceries`, `MiniCalendar`, `MiniCookbooks` and the after-planning step, with `IngredientPanel` in `components/ingredients/`. A panel only one feature opens belongs to that feature: `MiniRecipes` (the calendar page and today's meals) to calendar, the filters panel to library. Every panel reads its data through shared-react hooks, and `MiniGroceries` imports nothing from groceries' own code, so a feature `index.ts` that exports panels only added a lint exception and showed no real dependency. Features never import each other: lint blocks `@/features/<x>` everywhere outside feature `<x>` except route files, which import screens directly. Until library lands (19), `MiniGroceries` is still exported through `features/groceries/index.ts`. The cycle check runs madge in each workspace, so `@/` imports count.
- Pieces several features render that aren't panels go to the shared folders. `GroceryCheckbox` becomes `RoundCheckbox` in `components/`, with `isCheckboxEvent` beside it: the recipe card, a recipe's ingredients and the cookbook picker use it as much as the groceries list does, and only its Store colour is a groceries concern.
- Timers are shared code, not a feature: cooking mode and a recipe's timer chips start them, and the dock in the shell shows them on every page. The store moves from `stores/timers.ts` to `lib/`, the dock and the chip to `components/`. Mobile has no timers yet, so the store stays in web until it does.

### Web layout

- Web does not move into `src/`. `features/` sits next to `app/`; `server/` and `config/` stay where they are.
- Route files keep their server-only work (cache seeding, metadata, params) and render a screen from a feature. A page seeds only what its screen's first frame draws. Where routes share a layout, as the grocery list and the Pantry do, the layout renders the feature's root, which holds what the screens share (a header, the subscriptions) and draws the one the address names, so a switch stays on the client; the layout seeds the view a full load opens on, and each page only gives its view an address.
- A feature's `components/` is grouped by area (`list/`, `panels/`, `stores/` and so on), each area with an `index.ts` the screens and other areas import.
- The old `components/`, `hooks/`, `context/` and `stores/` folders stay and empty out feature by feature; whatever is left is deleted with the last feature.
- A feature's unit tests move into one flat `__tests__/` folder in the feature when it migrates (`features/<feature>/__tests__/` in an app, `src/<feature>/__tests__/` in shared-react), so they don't clutter its tree. Lint skips them, since the base ESLint config ignores `__tests__/` and `*.test.*`. Typecheck covers web's and mobile's tests, since their tsconfigs take the whole app; of the packages, `shared`, `shared-react` and `shared-server` exclude `src/**/*.test.*`, and the rest keep their tests outside the `src/` their tsconfigs include. The E2E suite stays under `__tests__/e2e`.

### State

- Server data is read through plain hooks over the Query cache, with `select` where a component needs a slice. It never lives in a context or a zustand store; the Query cache is its one source of truth (offline ADR-0001).
- TanStack tells a query's readers in a `setTimeout(0)` task, so a value written to the cache in a click renders one task after the click's own state changes, in a commit of its own.
- A read refetches on mount only when it may be behind. Web skips the server's seeded copy under the stale time and, until stale, a copy a mounted subscription keeps current (`useKeepsCurrent` in `realtime/`); config reads stay current through the admin's broadcast edits. A key a screen must keep while none of its observers is mounted, as the list's reads are while the Pantry view shows, gets a `gcTime` default in the Offline Cache.
- A write's rollback and settle go in `useMutation`'s own options, never in a `mutate` call's, which run for the last call only and would skip an overlapped one. The component that holds a `useMutation` renders on each of its status changes; its memoised children don't.
- A list keeps an unchanged item's object (`useStructuralSharing`, or a `select` the cache shares) and memoises its rows, so a change renders the rows it touches. A row skips what it doesn't draw: a grouped grocery row ignores its lines' sort order and version, which a create changes for every open line below it.
- A context remains only to hand down a per-page store (below) or for compound components (`Panel`, `Carousel`, DnD). Every reader renders when its value changes, so a compound component's context changes only while it is in use: the flat and the grouped list's DnD contexts hold a drag's arrangement and are otherwise constant, and each Store reads its containers off its own rows or groups. Both lists drag through one hook. dnd-kit itself measures drop targets only while a drag is on, and every `DndContext` takes a `useId` id.
- zustand holds client state shared across components. A store is global unless its first value comes from the request or the page; a global one that must start fresh per screen resets on unmount. A store holds ids, never a copy of server data: the edit panel holds its grocery's id and reads the grocery live.
- A store whose first value comes from the request or the page (the Library's filters from the reader's cookie, the recipe page's recipe id) is made per page: the page's provider creates it once with zustand's `createStore`, or, where pages share it, their root does, as library's makes the filters for the dashboard and the cookbook page, and hands it down through a context that holds only the store, and components read it with a selector. A module-level store is one object on the server, shared by every request, so it can't carry one reader's filters or one page's recipe while the server renders. The context's value is the same store for the page's life, so the context renders nothing; a changed slice renders only the components that select it, and the store goes when the page unmounts, with nothing to reset.
- A store both apps need lives in `shared-react/<feature>`; a store that is purely platform UI (web's `actionBarOpen`) stays in the app. A persisted store persists through the platform adapter's storage.
- Device Preferences stay on the profile (CONTEXT.md) and are server data like any other. They get their own `user.getDevicePreferences` query, seeded on a full load by the `(app)` layout, since the timer dock reads one on every page; `user.get` isn't seeded because its API-key metadata would sit in every document the worker keeps, and it stops carrying preferences so there is one copy. `useDevicePreference(key)` selects one preference, so flipping one re-renders only its readers; setting one is an optimistic mutation, one write at a time, through the Outbox while Offline. Hydration only overwrites with newer data, so a fresh server read beats an older restored copy and a newer local copy wins while Offline, replacing the context's hand-written precedence. Signed out or on a shared recipe there is no server copy, so a change stays in that cache entry for the visit and is never written. Device Kind is a platform fact and comes from the platform adapter.

### shared-react

- Organised by feature: `src/<feature>/` holds its hooks, client stores, realtime subscription and types, exported as `@norish/shared-react/<feature>`. Domains are coarser than app features: `shared-react/recipes` holds the list, filters, selection, a recipe, the recipe page's store, favourites, ratings, shares and cookbooks, and `features/library` and `features/recipes` import it. Cookbooks sit there because a cookbook change also rewrites the cookbook labels in every cached library page, and a recipe change rewrites the cached library pages, so library and recipes can't be separate shared-react features without importing each other.
- Cross-cutting folders: `trpc/`, `platform/`, `offline/` (already there; it also takes `optimistic-updates.ts`, which keeps an optimistic change whose write was Queued in the Outbox, so every feature's mutations import it from there), `config/` (reference data: units, tags, categories, cuisines, recurrence, upload limits, and the ingredient catalogue's realtime subscription, which marks every read derived from an Ingredient stale after a merge, rename or nutrition correction), `reader/` (the signed-in Reader: identity, household, active allergies, permissions, Device Preferences), and `realtime/` (the hook every feature's realtime subscription is built on, so each one recovers from a lag the same way).
- Features never import each other; cross-cutting folders never import features. Lint enforces both.
- The recipe query inputs (`filter-contract`, `list-queries`) are pure contracts, so they move to `@norish/shared/contracts`. The offline Warm Set and `shared-react/recipes` import them from there, and the server's cache seeding stops importing a React package.
- `createTRPCContext<AppRouter>()` runs once at module level in `trpc/`, so every hook imports `useTRPC`. `createTRPCProviderBundle` stays a factory for each app's config only (links, WebSocket implementation, QueryClient, outbox link) and provides that one context.
- Whatever draws data mounts the subscriptions that keep it current: a feature's root for its screens, a panel for itself while it is open, and the shell for what it draws itself plus the Reader. A screen that draws another domain's data mounts that domain's subscription too, so its root lists everything it depends on, and a mobile screen mounts the same hooks. Each handler updates the reads of what mounts it; two mounts of one subscription handle an event twice, which idempotent merges make harmless. Settled with library, replacing "in the shell when screens outside the feature show the data", which left the shell holding four domains' subscriptions it never draws:
  - The shell: the Reader's (household, permissions), admin config (the timer dock reads `timersEnabled` and the language list `localeConfig` on every page) and the recipe import outcomes with their toasts, since an import starts from the avatar menu or the copied-link prompt on any page.
  - Library's root: the recipe list events, ratings, cookbooks, and the Pantry, which orders the Library by pantry share.
  - The recipe page: its recipe, shares, enrichment, ratings, cookbooks (its cookbooks card) and the ingredient catalogue. The editor: the ingredient catalogue.
  - Groceries' root: groceries, Stores, the Pantry and the ingredient catalogue.
  - Calendar's context, on the calendar page and in today's meals: the calendar and recipe renames, which change a planned recipe's name and image.
  - The user settings page: the archive import. The ingredient settings page: the ingredient catalogue.
  - Panels, while open, and a panel mounts its content only while open: `MiniGroceries` groceries, the Pantry and the ingredient catalogue; `MiniCookbooks` cookbooks; `MiniRecipes` the recipe list events; `MiniCalendar` the calendar, as it already did; `IngredientPanel` the ingredient catalogue, the Pantry and groceries.
- Away from a screen nothing keeps its reads current, so coming back refetches them while the cached copy shows; `library.list` gets a `gcTime` default so the grid outlives a long cooking session.
- Each layout seeds only what its screens draw, the `(app)` layout included: it seeds permissions (the AI-key prompt and the import modal read them on every page) and Device Preferences (the timer dock). The household and the reader's allergies are seeded by the Library's and the recipe page's layouts, which draw them, through one helper.
- One platform adapter, mounted once per app, carries toasts, navigation, error display, storage, Device Kind and, from recipes on, the session and sign-out. It grows as features migrate.
- shared-react compiles under each app's React Compiler. The compiler skips a whole hook or component it can't compile, for a logical assignment (`||=`, `&&=`, `??=`), a `finally` or a conditional, logical or optional-chaining expression inside a `try` among others, and lint reports every skip through `eslint-plugin-react-hooks`, pinned to the release that bundles the build's compiler. A `try` with branches sits in a plain function the hook calls, as in 07's `useRecurrenceDetection`. It also memoises nothing an options object passed to a hook captures when the object is built between hooks, so options are built before the first hook that takes them. Likewise a value made before a hook isn't memoised when a call after the hook could mutate it, such as one of its rows handed to a callback prop, so the flat list's drag overlay calls `getRecipeNameForGrocery` in a component of its own.
- The pilot is a clean migration: groceries reads nothing from web's old contexts. So `reader/` starts in the groundwork with Device Preferences, which groceries needs; identity, household, active allergies and permissions join it with recipes, whose page reads allergies and permissions. Each app hands the Reader its session and sign-out through the platform adapter: web its better-auth session with the server's seed, mobile its auth context, which stays because it owns the client. Both apps' `UserContext`s and `createUserContext` go, and so do the household and permissions contexts.
- The `create*Hooks` and `create*Context` factories, each app's binding files, and the `./hooks` and `./contexts` exports go away feature by feature and are gone with the last one.

### Recipes (the second feature)

- `features/recipes` holds the recipe page, the editor (new and edit), cooking mode, and the shared recipe page. The read-only pieces both recipe pages render (ingredients, steps, sections, nutrition, the mobile header, cooking time, source, the amount toggle, the page tint) are recipes' own. Pieces the Library also renders (the heart, the delete modal, the double-tap container, the origin flag, the cookbook icon, the swipeable row) go to the shared folders. `MiniCookbooks` and `MiniCalendar`, which the recipe page opens, stay where they are until library and calendar move.
- `shared-react/recipes` takes the whole recipe domain at once, since it is one domain: the list and library reads, the pending imports, the recipe mutations, favourites, ratings, shares, cookbooks, a recipe and its subscription, enrichment, conversion, images, videos, autocomplete and the random pick, as plain hooks exported as `@norish/shared-react/recipes`. Web's and mobile's recipe bindings go. `RecipesContext` stays in the shell until library, fed the plain hooks, and the recipe page and the editor stop reading it: favourites, deletes and the editor's create and update come from the plain hooks.
- The recipe page's context becomes the per-page store: the page's provider makes it from the page's recipe id and it holds the id, the servings the reader picked, the conversion choice and the wake lock. The live route hands the provider its params, and the offline bootstrap hands the same page the same params for a Warm Set recipe. The recipe, its shares, ratings, the reader's favourites, enrichment and the recipe's cookbooks are read through hooks by id; the page mounts the recipe's, its shares' and its enrichment's subscriptions. The wake-lock context folds into the store. The detail context's unread fields go: `liked`, `toggleLiked`, its own `userRating` and `rateRecipe`, `createShare`, `updateShare`, `refreshShares`, `shareError` and `reset`.
- The shared recipe page's provider becomes the same kind of per-page store, holding the share token, the servings and the measurement system; the shared recipe is read through a hook by token. Signed out there is no Reader, as today.
- The ingredient icons leave their context: each `IngredientIcon` selects its own icon from the icons query over the Query cache, so a food joining a list renders that food's icon only. `IngredientIconsProvider` goes from every place that mounts it: the recipe page, the editor, the shared recipe page, the ingredient settings and the groceries screens.
- Mobile's smoke screen reads the Reader's identity and the recipe total through the same hooks, with no binding.
- Dead code goes with it: `useRecipeFilters`, `useCookbooksQuery`, `useCookbooksCacheHelpers`, `useServerSettingsQuery` and the unused `createUseAmountDisplayPreference`.
- Nothing visible changes, but for what seeding only the first frame brings, as in the pilot.

### Library (the third feature)

Settled 2026-11-10; tickets 16–19.

- `RecipesContext` goes. From the shell it read `library.list` and the pending imports on every page, though only the dashboard draws them. Its readers use the plain hooks: the list, the pending imports, favourites, deletes, and the imports the avatar menu, the copied-link prompt and the search field start. `mobileSearchOpen` goes, since nothing sets it, with the context's ten unread fields (`isValidating`, `error`, `isFetchingMore`, `hasMore`, `favoriteIds`, `loadMore`, `createRecipe`, `updateRecipe`, `invalidate`, `openRecipe`).
- The cookbook page moves under `(library)`, its URL unchanged. `(library)/layout.tsx` reads the filters cookie, seeds what both pages draw (favourites, the household and allergies) and renders library's root around them. `(library)/(dashboard)/layout.tsx` seeds today's week, `library.list` and the pending imports, so a full load of a cookbook doesn't seed the dashboard's reads, and `cookbooks/[id]/layout.tsx` seeds the cookbook as before. Unlike groceries' root, library's wraps its pages instead of drawing them by address: a cookbook is a drill-down, and its layout seeds it on navigation.
- The filters are a per-page store library's root makes from the cookie, so the dashboard and a cookbook page keep sharing them. The recipe page's back link names the Library's type from one value its route reads from the cookie (the offline bootstrap reads the browser's), not from the store.
- Selection is a global store in `shared-react/recipes`, so mobile's multi-select reuses it. It holds what the context held, each selected recipe's id, version and owner, since a search can hide a selected card and a delete still needs its version. Each screen resets it on unmount, so a selection doesn't follow the reader into a cookbook. The recipe events drop deleted ids from it, replacing the selection context's own `onDeleted` subscription. The delete animation and Escape-to-clear stay in web. `actionBarOpen`, which hides the mobile nav and the floating chip while the selection bar is open, moves from `stores/useAppStore.ts` to `lib/`.
- Subscriptions follow the rule above. The recipe events split: the import outcomes (`onImportStarted`, `onImported`, `onFailed`) in the shell, the list events (`onCreated`, `onUpdated`, `onDeleted`, `onDeleteKept`, `onConverted`, `onRecipeBatchCreated`) in library's root. The calendar invalidation leaves the list events for calendar's own rename listener.
- Seeds follow the rule above: the `(app)` layout keeps permissions and Device Preferences; favourites, the household and allergies move to the `(library)` and recipe layouts; the pending imports to `(dashboard)`. The avatar menu's language switch reads the saved locale only when the menu opens, so the navbar stops reading `user.get` and the allergies on every page.
- The dashboard's route composes today's meals and the Library: it renders today's meals, calendar's, above the library screen, since `features/library` can't render calendar's code. Today's meals and `MiniRecipes` stay where they are until calendar.
- `features/library` holds the dashboard's Library, the cookbook page, the filters panel, the selection bar and their components, and has no `index.ts`. `MiniCookbooks` stays in `components/Panel/consumers/`, and `MiniGroceries` moves back there from groceries, whose `index.ts` and the lint exception for it go.

### Migration

1. Groceries (the pilot).
2. Recipes, with the shared recipe page. The Reader's identity, household, allergies and permissions and the whole `shared-react/recipes` domain move first, and the ingredient icons move here: the recipe page, the editor and the shared recipe page all draw them.
3. Library, with the cookbook page, the subscription and seeding rules, and the shared panels.
4. Calendar.
5. Settings.
6. Imports and auth.

The pilot's numbers are recorded in tickets 03 and 07. A problem with the shape itself amends this spec before the next feature starts. The pilot found none (07): groceries sits in `features/groceries` on web and `shared-react/groceries`, mobile's smoke screen reads the same hooks with no binding, and the rules it taught are folded into the sections above. Its one adjustment was letting shared code open a feature's panel through `index.ts`. Recipes' grilling added two rules: a per-page store handed down through a context, and a shell that mounts only what it draws. Library's changed two: whatever draws data mounts its subscriptions, another domain's included, and a panel several features open lives in the shared folders. Later features aren't measured. The mobile rewrite builds each screen once its feature has migrated, and mobile's catch-up spec line "Web keeps its current layout" points here.

## Testing Decisions

- A good test drives a hook or store through its public interface and asserts what a caller observes: the data returned, what the cache holds after a mutation or a realtime event, what a store holds after an action. Never internal calls.
- shared-react's existing groceries, stores and pantry suites (`store-prices-pending`, `store-aisles`, `pantry`) move next to the code and run against the plain hooks.
