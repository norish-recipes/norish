Built (option A, 2026-11-15):
1. The Outbox link's per-entity order and version rewrite are gone. `recipes.update` is the one "whole edit" path the engine names. A save of a recipe with a pending entry goes to the Outbox, not live. If that entry is still pending, never attempted (`attempts` 0) and not being sent, the save replaces its input, operationId and headers in one atomic change of the stored entry (`outbox.change`: one IndexedDB transaction on web, one synchronous MMKV read and write on mobile), on the entry's version. Otherwise the save queues as its own entry. A live save that fails is stored as its own entry, like every other write, and never replaces one; two live saves that both fail replay as two entries and the second is refused and told (the accepted gap).
2. A save takes no lock, so it never waits on Replay or the Cache Warmer. Replay marks an entry `sending` in one atomic change before it sends it, and sends what that change read; the replace refuses a marked entry, so the two never race. The mark clears on every outcome that leaves the entry pending, and names the store (one per launch or tab) that set it: another one's mark counts only while some context holds the Replay lock (web: another tab), so a mark left by a kill or a closed tab does not block the replace. Every write to an entry (park, attempts, unmark) is one atomic `change`; the adapters' `get`/`put` are gone. Whole edits record no entity id, so a parked edit never parks a favourite, rating, planned item or grocery add of that recipe.
3. A live save the server refuses stores nothing: Recovery tells its listeners (once per run, joined with a batch's refusals), the controller toasts and invalidates so what is on show refetches, and the hook rolls back its own optimistic state; when another edit of that recipe is still waiting, the recipe refetches once those settle. Replay still parks a refused queued edit as Conflicted (ADR-0004).
4. An applied answer writes its version to the cached recipe (never lower) only while the cache still holds this save's optimistic state; otherwise that recipe refetches. A convert or a later edit made from that cache is sent on that version. Step rows reach their ref in a layout effect (web and mobile). Their `version` still rises on every save, as the repository does for any line it keeps.
