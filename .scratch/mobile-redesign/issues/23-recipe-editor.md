- 2026-11-15 re-review round. Queued edits, the design (replaces the predicted version):
  1. The client sends only versions the server handed out; `recipes.update` answers `{ stale, version }` once stored.
  2. The Outbox link sends one entity's edits (`{ id, version }`) one at a time, live and replayed alike.
  3. An answer `{ stale: false, version }` moves the later edits sent on the same base to that version, in memory and in the stored Outbox before the answer passes on, so a restart between replays keeps them.
  4. Only our own writes are skipped over: an edit on a base another member changed is refused, the recipe is refetched and the toast "Not saved: it changed elsewhere first" shows once (live in the hook, after Replay from Recovery's conflict listener).
  Also: a failed edit leaves a later one's state alone; an edit on a version the cache has passed is not shown; photos join outside state updaters and order from the current value; every upload path releases Save and a hanging photo shows as a removable tile; every library pick asks for the compatible (JPEG) form; the pill lets taps through while the `@` popup is open; a focused field is revealed again when the content grows.
