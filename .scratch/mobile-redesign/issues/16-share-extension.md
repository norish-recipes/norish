## Comments

### Design (settled before code, 2026-11-13)

1. **Target:** `@bacons/apple-targets` (5.0.0, the plugin Expo's own App Clip guide uses) links `apps/mobile/targets/share/` as a `share` target at prebuild: our code is a 10-line `expo-target.config.js`, the extension's `Info.plist` and the Swift files; a hand-written plugin would be ~200 lines of pbxproj edits (target, phases, embed, configurations). Added with `pnpm add -D` (the workspace's way; `expo install` has no pin for it) and kept out of autolinking, since its `ExtensionStorage` native module is unused. SwiftUI, no React Native.
2. **Shared:** one App Group, `group.dev.norish.app`, declared once in `app.json`'s `ios.entitlements`; the target's `expo-target.config.js` hands it to the extension (corrected 2026-11-14: apple-targets mirrors the group only when the target config declares `entitlements`), JS finds it and its container in `Paths.appleSharedContainers` (expo-file-system, fed by autolinking from the entitlements), Swift derives it as `group.` + the containing app's bundle id. On iOS an App Group is itself a keychain access group, so no `keychain-access-groups` entitlement and no team id. SecureStore items move to `keychainService: "norish.shared"` (stored as service `norish.shared:no-auth`), account = the key's UTF-8, access group = the App Group, `WHEN_UNLOCKED` (today's class; readable only while unlocked). Keys: `norish.backend-base-url`, `norish_cookie`, `norish_session_data` and Better Auth's chunk keys. The Server Address moves too: one store, one move, one wipe. Swift only reads the address and the cookie (resolving Better Auth's `ba-chunks:` marker) and never writes; the cookie never touches the App Group's files.
3. **Move:** `loadServerAddress` (the boot's first SecureStore read) awaits a once-per-launch move. A different service keeps old (`app`) and new items apart whatever group a query names. Marker `norish_keychain_moved` in the shared store: present → delete old leftovers, use shared; absent → copy every old logical value into shared, read each back and compare, write the marker, then delete the old items (base + chunk keys). Any throw before the marker → this launch keeps the old store (still signed in), the next launch copies again with the old store as the truth. Android keeps today's store. Unit-tested as a function over two fake stores.
4. **Session end:** Sign-out, Session Expiry, an account switch, a Server Address change and the wipe all end in `clearAuthStorage`, which now names the shared store, so the shared cookie goes with them. Reads, writes and the in-memory cookie cache (`088df2fc6`) go through the same wrapper with the options added; a refreshed cookie is written there as before.
5. **Requests:** health first (`GET /api/v1/health`, no cookie): no HTTP answer → saved; not Norish → failed; version below the containing app's `major.minor.0` (the gate's `MINIMUM_SERVER_VERSION`) → too old. Images then ask `permissions.get` (`isAIEnabled`, as the app does) → AI off line. Then tRPC v11 `httpLink` shapes: `POST /api/trpc/recipes.importFromUrl` and `.importFromPaste` with superjson `{"json":{…}}`, `.importFromImages` as multipart `file0…fileN` (the form-data link sends FormData raw). There is no client-version header; the gate reads health. Cookie set by hand on an ephemeral `URLSession` with no cookie storage, sent only to the Server Address's origin; a redirect to another origin is refused. Sent only on a 200 whose body has `result.data`; 401 → signed-out line.
6. **Offline:** no HTTP answer → `<group>/share-inbox/<id>.json` (`kind`, `url`/`text`/`images` file names, `savedAt`) with images `<id>-<n>.jpg` written first, the JSON last. The signed-in shell drains on mount and on foreground through `useImportRecipe` (ticket 15's sheets' hook): an item's files go once the import succeeded or sits durably in the Outbox (or the server refused it for good); 401 or a failed admission keeps it. One drain at a time (module scope), items one by one; a corrupt item is removed.
7. **Strings:** keys under `recipes.shareExtension` in every locale; a local config plugin writes `targets/share/Localizable.xcstrings` (gitignored) from `packages/i18n` at prebuild, catalogue codes mapped as `CFBundleLocalizations` does (`de-informal`→`de`, `no`→`nb`).
8. **Device only:** the real share sheets' memory limit (images are downscaled with ImageIO one at a time), the move from a team-signed build, the lock-state class. A device build needs the App Group `group.dev.norish.app` on the maintainer's team for `dev.norish.app` and `dev.norish.app.share` (Xcode's automatic signing registers it) and a team chosen locally; nothing in the repo names a team.

### Implementation (2026-11-14)

- Deviations: iOS hosts a share extension in a full-height sheet and ignores detents, `preferredContentSize`, `modalPresentationStyle` and `NSExtensionActionWantsFullScreenPresentation` (Action extensions only), all tried on the simulator; the extension clears its in-process containers' backgrounds in `viewIsAppearing` and draws the board's scrim and content-height glass card at the bottom itself, and Safari's share sheet stays visible under the scrim. A 502/503/504 on the health check counts as unreachable (a proxy in front of a stopped server). Saved items carry their Server Address and the drain drops one saved for another server. The shared import functions take an optional `onSettled`, fed by `mutateAsync`, so the drain knows when an item is durable.
- Small board differences: the photos row has no "From Photos" line (an extension cannot know the source app); a link already in the library reads as sent.
- Left undone: the device hand-check; on the simulator the too-old, AI-off and failure lines were not seen (they need an older server, AI turned off on the maintainer's server, or a non-Norish answer), and "Sending" only mid-slide in light (a local server answers before the card settles).
- Unsigned: the signing agent stayed locked, so this ticket's work is uncommitted; the commit order and paths are in the run's `t16/commit-plan.md`.
