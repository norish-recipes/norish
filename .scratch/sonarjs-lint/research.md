# eslint-plugin-sonarjs: what other tools ship by default

Researched 2026-10-14 for the plan in `spec.md`. Primary sources only: package tarballs, GitHub source at named commits, SonarSource docs and the SonarJS repository.

Versions read:

- `eslint-plugin-sonarjs` 4.2.2 (installed copy in `tooling/eslint/node_modules/eslint-plugin-sonarjs`; npm `gitHead` aebf8d46, SonarJS commit of 2026-09-28), plus tarballs 3.0.5, 3.0.7 and 1.0.4 for the configs pinned to older lines.
- SonarJS repository at commit [aebf8d46](https://github.com/SonarSource/SonarJS/tree/aebf8d46933ec80ff3437ceb69e320b5a97b7108), the commit 4.2.2 was published from.
- SonarQube Server 2026.4 and 2026.5 docs and SonarQube Cloud docs, as served on 2026-10-14.
- `eslint-config-hardcore` 50.1.0, `eslint-config-sheriff` 31.4.0, `@antfu/eslint-config` 9.5.1 (npm tarballs).
- Application and library repos at their default-branch HEAD on 2026-10-14: podman-desktop, swiftlang/vscode-swift, grafana/metrics-drilldown, shuding/nextra, bvaughn/react-resizable-panels, ag-grid/ag-charts, DestinyItemManager/DIM.

## Summary

- **There is no single "default".** The plugin's `recommended` is exactly SonarQube's old "Sonar way" profile, restricted to the rules the plugin ships (230 of 295). But SonarQube itself no longer defaults to that profile: since Server 2026.5 and on SonarQube Cloud, new projects get **Sonar way core**, and the old "Sonar way" is now called **Sonar way comprehensive**. By my derivation, core holds about 129 of the 230 rules. It leaves out `cognitive-complexity`, every nesting rule, `todo-tag`, `deprecation`, the unused-code rules and most style rules. It keeps the security rules and the medium-and-up bug rules.
- **SonarQube scopes rules in ways the ESLint preset does not.** Each rule has a scope (Main or Tests) and a language (JS, TS or both), and the analyzer filters on both. The preset has no `files` key, so every rule runs on every file. For Norish (TypeScript) this matters in three places:
  - `no-unused-vars`, `different-types-comparison` and `function-return-type` are Sonar way rules for JS files only. Together they have 37 Norish findings, which SonarQube would not raise on `.ts`/`.tsx`.
  - Main-scoped rules such as `cognitive-complexity`, the nesting rules and `todo-tag` do not run on test files in SonarQube.
  - `prefer-read-only-props` and `use-type-alias` are Sonar way rules for TS only.
- **Security hotspots no longer exist in the analyzer metadata.** At the 4.2.2 commit, no JS/TS rule has type `SECURITY_HOTSPOT`. The four Norish hits (`pseudo-random`, `no-clear-text-protocols`, `file-permissions`, `no-os-command-from-path`) are `VULNERABILITY` with a `former-hotspot` tag. SonarSource's docs say hotspots are being moved to vulnerabilities. In SonarQube they are now issues to fix, not review items, which matches how the ESLint plugin treats them: plain errors.
- **Configs that extend the preset mostly loosen it.** Six of the sampled projects extend a v3/v4 `recommended`; four more use the v1 preset (sheriff, DIM) or hand-picked rules (hardcore, antfu). Common changes:
  - `cognitive-complexity` is turned off in 5 of 10 (sheriff, podman-desktop, nextra, react-resizable-panels, DIM). It is downgraded to warn in ag-charts and kept at error at 15 in vscode-swift and in antfu's opt-in set. It is tightened to 11 in metrics-drilldown and to 10 in hardcore.
  - `no-nested-conditional` is off in 3 of the 6 v3/v4 preset users. hardcore and sheriff use ESLint core `no-nested-ternary` instead.
  - `todo-tag` is off or warn in all 6 v3/v4 preset users.
  - `deprecation` is off in 3 and warn in 1. `no-unused-vars` is off in 3 (nextra, react-resizable-panels, ag-charts); ag-charts labels it a duplicate of typescript-eslint.
  - Every project that extends the preset also turns on type information.
- **Where Norish sits.** Norish keeps the preset as shipped, as errors, everywhere. That matches swiftlang/vscode-swift and Grafana's metrics-drilldown most closely. Rule by rule:
  - **Same as the plugin and as Sonar way comprehensive:** `cognitive-complexity` 15, `no-nested-*`, `pseudo-random` and the other former hotspots, `deprecation`, `unused-import`, `no-small-switch`, `no-duplicate-string` off.
  - **Stricter than half or more of the six v3/v4 preset users** (count that relax it in brackets): `todo-tag` (6), `function-return-type` (5), `cognitive-complexity` (4), `deprecation` (4), `different-types-comparison` (4), `use-type-alias` (4), `no-nested-conditional` (3), `no-nested-functions` (3), `no-unused-vars` (3).
  - **Stricter than SonarQube's own default (core):** every maintainability rule in the plan, plus the language and test scoping above.
  - **Looser than Sonar way, the plugin, nextra and metrics-drilldown:** `prefer-read-only-props` off. Only react-resizable-panels also turns it off.
  - **Looser than hardcore and metrics-drilldown:** the complexity threshold (15 against 10 and 11).
- **One correction to `spec.md`.** The plugin has 71 rules that need type information, but only 57 of them are in `recommended`. Without type information, 28 of those 57 report nothing and 29 fall back to a weaker syntax-only check.

## 1. eslint-plugin-sonarjs 4.2.2, `recommended`

Read from the installed copy (`tooling/eslint/node_modules/eslint-plugin-sonarjs`) by loading `cjs/plugin.js` and each rule's `generated-meta.js`.

- **Counts.** 295 rules; `recommended` sets 230 to `"error"` and the other 65 to `"off"`. There is no `"warn"`. Source, `cjs/plugin.js`:
  ```js
  for (const [key, rule] of Object.entries(plugin_rules_js_1.rules)) {
    const recommended = rule.meta?.docs?.recommended || false;
    recommendedConfig.rules[`sonarjs/${key}`] = recommended ? "error" : "off";
  }
  ```
- **What decides "recommended".** Membership in SonarQube's "Sonar way" profile for either language. SonarJS `tools/generate-eslint-meta.ts` writes `___RECOMMENDED___: \`${isInSonarWay(ruleRspecMeta.defaultQualityProfiles)}\``([source](https://github.com/SonarSource/SonarJS/blob/aebf8d46933ec80ff3437ceb69e320b5a97b7108/tools/generate-eslint-meta.ts#L66)).`isInSonarWay`is documented as "ESLint exposes one shared recommended config rather than per-language configs, so a rule is recommended when any language includes it in Sonar way" ([quality-profiles.ts](https://github.com/SonarSource/SonarJS/blob/aebf8d46933ec80ff3437ceb69e320b5a97b7108/packages/analysis/src/jsts/rules/quality-profiles.ts)). I checked all 295 rules against the rule metadata JSON:`recommended` equals "in Sonar way for JS or TS" with no exception.
- **Why the 65 are off.** No per-rule reason is documented; the README only says the preset "enables most of the rules except for a few exceptions". By the mechanism above, a rule is off because it is not in Sonar way. 13 of the 65 are deprecated (`os-command`, `no-mixed-content`, `hidden-files`, `confidential-information-logging`, among others). The rest are opt-in style or strictness rules such as `no-duplicate-string`, `cyclomatic-complexity` [10], `max-lines` [1000], `no-commented-code`, `elseif-without-else` and `no-collapsible-if`.
- **`cognitive-complexity`.** Default threshold 15: `defaultOptions: [15]` in the rule meta, and `default: 15` in [S3776/config.ts](https://github.com/SonarSource/SonarJS/blob/aebf8d46933ec80ff3437ceb69e320b5a97b7108/packages/analysis/src/jsts/rules/S3776/config.ts). `no-nested-functions` defaults to `{ threshold: 5 }`, raised from 4 in 4.2.1 (changelog JS-2125).
- **Type information.** 71 rules have `meta.docs.requiresTypeChecking: true`, and 57 of them are in `recommended`. The guard is `helpers/parser-services.js`: `return !!services?.program;`. I classified each typed rule by reading its `create()`:
  - **Silent without type information** (return `{}`): 28 recommended rules. Among them are `deprecation`, `different-types-comparison`, `function-return-type`, `no-alphabetical-sort`, `prefer-regexp-exec`, `jsx-no-leaked-render`, `no-misleading-array-reverse`, `no-try-promise`, `no-undefined-argument`, `prefer-read-only-props` and `null-dereference`.
  - **Weaker check without type information:** 29 recommended rules. These include the 15 regex rules built on `helpers/regex/rule-template.js`, which still check regex literals and `RegExp` constructors but skip string patterns passed to `str.match('...')` and similar. Also in this group are `unused-import`, `no-small-switch`, `void-use`, `assertions-in-tests`, `arguments-order` and `sql-queries`.
  - This means a config without type information silently loses about a quarter of the preset. It also explains why `prefer-read-only-props` and `deprecation` only appeared once Norish turned on `projectService`.
- **Other settings.** The preset sets no `files`, no `languageOptions` and no parser, so it applies to every file ESLint lints. It does set `settings: { react: { version: '999.999.999' } }`, which ends up in the shared settings object that any plugin reading `settings.react.version` will see. The README asks users to configure `@typescript-eslint/parser` themselves.
- **Not the whole of SonarQube.** The README states the plugin "does not contain all the rules from the SonarQube JS/TS analyzer". It lists 169 rules SonarQube runs through other ESLint plugins unchanged and 119 "improved" (decorated) ESLint rules the plugin does not ship.

## 2. SonarQube "Sonar way" for JS/TS

**Profiles.** SonarQube Server 2026.5 and SonarQube Cloud now ship three built-in profiles per language: Sonar way core, extended and comprehensive.

- [Server docs](https://docs.sonarsource.com/sonarqube-server/quality-standards-administration/managing-quality-profiles/built-in-quality-profiles.md): "**Sonar way core** is the default quality profile for every language" and "Sonar way comprehensive replaces the quality profile formerly named **Sonar way**."
- Upgraded Server instances keep their old default: "When you update to SonarQube Server 2026.5 from an earlier version, your projects keep the quality profiles they used in the previous version. The default profile of each language also stays the same." The [Cloud page](https://docs.sonarsource.com/sonarqube-cloud/standards/managing-quality-profiles/built-in-quality-profiles.md) says the same for existing organizations.
- The docs define each tier by rule severity:
  - **Core:** "All security rules", "Medium and higher severity recommended reliability rules", "Blocker severity recommended maintainability rules".
  - **Extended:** all security rules, "Low and higher" reliability, "High and higher" maintainability.
  - **Comprehensive:** all recommended rules.

**Sonar way contents.** I downloaded the 582 JS/TS rule metadata files from [the SonarJS repo at the 4.2.2 commit](https://github.com/SonarSource/SonarJS/tree/aebf8d46933ec80ff3437ceb69e320b5a97b7108/sonar-plugin/javascript-checks/src/main/resources/org/sonar/l10n/javascript/rules/javascript). The repository still calls the profile "Sonar way", which is the comprehensive tier.

- Sonar way holds 424 non-deprecated rules for JS and 439 for TS, 463 in their union.
- The plugin's 230 recommended rules are all in it. The other 233 Sonar way rules are external or decorated ESLint rules that the plugin does not ship.
- I derived the **Tier** column by applying the documented definitions to each rule's `code.impacts`. Examples:
  - `cognitive-complexity`: `{"MAINTAINABILITY": "HIGH"}`, so extended.
  - `no-nested-conditional`: `MEDIUM`, so comprehensive only.
  - `todo-tag`: `INFO`.
  - `pseudo-random`: `{"SECURITY": "MEDIUM"}`, so core.
  - By this derivation, 129 of the 230 recommended rules are in core and 145 in extended.

**Threshold.** `cognitive-complexity` defaults to 15 in SonarQube as well; it is the same `S3776/config.ts` default that feeds the analyzer.

**Type information.** The analyzer creates TypeScript programs itself, so a SonarQube user configures no parser. The [changelog](https://github.com/SonarSource/SonarJS/blob/aebf8d46933ec80ff3437ceb69e320b5a97b7108/packages/analysis/src/jsts/rules/CHANGELOG.md) lists "Implement direct TypeScript program caching" (JS-946, 3.0.7) and "Use trie-based directory grouping for TypeScript program creation" (JS-1337, 4.0.1).

**Language and test scoping.** The analyzer turns a rule on for a file only when both of these hold:

- the language matches: `ctx.fileLanguage === (ruleConfig.language ?? 'js')` ([filter-language.ts](https://github.com/SonarSource/SonarJS/blob/aebf8d46933ec80ff3437ceb69e320b5a97b7108/packages/analysis/src/jsts/linter/filters/filter-language.ts));
- the file type is one of the rule's targets: `ruleConfig.fileTypeTargets.includes(ctx.fileType)` ([filter-file-type.ts](https://github.com/SonarSource/SonarJS/blob/aebf8d46933ec80ff3437ceb69e320b5a97b7108/packages/analysis/src/jsts/linter/filters/filter-file-type.ts)).

Each rule's `scope` (Main or Tests) and `compatibleLanguages` drive those filters. Of the 230 recommended rules, 196 are Main and 34 are Tests. The recommended rules that Sonar way applies to one language only:

- **JS only:** `argument-type`, `array-callback-without-return`, `different-types-comparison`, `function-return-type`, `future-reserved-words`, `in-operator-type-error`, `inconsistent-function-call`, `no-extra-arguments`, `no-implicit-global`, `no-trivial-assertions`, `no-unused-vars`, `null-dereference`, `prefer-single-boolean-return`, `updated-const-var`.
- **TS only:** `no-duplicate-in-composite`, `no-duplicate-test-title`, `no-fixed-wait-in-tests`, `no-redundant-optional`, `no-undefined-argument`, `no-useless-intersection`, `parameterized-tests`, `prefer-read-only-props`, `prefer-specific-assertions`, `prefer-type-guard`, `public-static-readonly`, `redundant-type-aliases`, `use-type-alias`.

The ESLint plugin's own metadata carries the same information (for example `exports.languages = ['js']` in `S3403/generated-meta.js` for `different-types-comparison`), but `recommended` ignores it.

**Security hotspots.**

- [SonarQube Server 2026.4 docs](https://docs.sonarsource.com/sonarqube-server/2026.4/user-guide/security-hotspots.md) define the difference as "_the need for review_ before deciding whether to apply a fix". A hotspot is reviewed and marked To review, Acknowledged, Fixed or Safe. A vulnerability "needs to be fixed immediately".
- The same page, and the [Cloud page](https://docs.sonarsource.com/sonarqube-cloud/managing-your-projects/issues/reviewing-security-hotspots.md), say: "To simplify the classification of findings, we are gradually transitioning security hotspots to vulnerabilities. As a result, rules that previously raised security hotspots will start raising vulnerabilities (in Standard Experience) or security issues (in MQR Mode)."
- SonarSource's announcement on its community forum ([2026-03-31](https://community.sonarsource.com/t/moving-security-hotspots-to-security-issues/180583)) says hotspots will count toward the Security Rating once migrated. It also says migrated findings get a `former-hotspot` tag.
- In the rule metadata at the 4.2.2 commit, no rule has type `SECURITY_HOTSPOT`, and 51 rules carry `former-hotspot`. Examples:
  - `pseudo-random` (S2245): `VULNERABILITY`, `{"SECURITY": "MEDIUM"}`.
  - `no-clear-text-protocols` (S5332): `VULNERABILITY`, `LOW`.
  - `file-permissions` (S2612): `VULNERABILITY`, `MEDIUM`.
  - `no-os-command-from-path` (S4036): `VULNERABILITY`, `LOW`.
  - `slow-regex` (S5852): `VULNERABILITY`, `HIGH`.
  - `no-hardcoded-ip` (S1313): `CODE_SMELL`, `SECURITY: LOW`.
  - All are in Sonar way and, being security rules, in core.
- In the ESLint plugin they are ordinary `"error"` rules (meta `type: 'problem'`), with no review state. An `eslint-disable` with a reason is the nearest equivalent of SonarQube's old "Safe" status.

## Could not verify

- **Tier column.** It is derived, not read. I applied SonarSource's documented tier definitions to each rule's `impacts` in the SonarJS metadata. I had no SonarQube instance or API to export the actual core and extended profiles, and the docs do not say exactly how a rule with several impacts is placed.
- **How the hotspot migration shows up in a given product version.** The docs say "gradually", and the dates come from a SonarSource forum post, not a release note. The rule metadata at the 4.2.2 commit is fully migrated. What an older SonarQube Server shows for these rules depends on its own analyzer version.
- **Scoping in a running SonarQube.** That SonarQube skips JS-only rules on `.ts` files and Main rules on test files is read from the analyzer's filter source and rule metadata, not observed on a running instance. Which files count as tests depends on the project's `sonar.tests` setting.
- **Behaviour without type information.** I classified the typed rules by reading each rule's source with a script, not by running them.
- **The application sample is not exhaustive.** GitHub code search caps results at 100 per query and 10 queries a minute, and it only finds configs whose text matches. I found no exhaustive "dependents" list.
- **Older config versions.** I checked the shared configs' dependency fields only for the latest versions, not their history.
- **Resolved plugin versions.** For configs with a caret range (`^3.0.5`, `^4.2.2`), I read 3.0.7 or 4.2.2 for rule membership. A consumer's lockfile may hold an older patch.
- **tridactyl** (6.4k stars) uses `plugin:sonarjs/recommended` with `^0.25.1`, a pre-1.0 line with different rule names. I left it out of the table.
