# Norish issues every model request through one runtime

Norish's AI code had no boundary. A module that looked like an internal AI API — an executor with `execute`, `executeText` and `executeVision` — had **no callers anywhere in the repository**, while all ten places that generate structured output imported `generateText` from the SDK directly and hand-rolled the same forty lines around it: the enabled check, model selection, Generation Preferences, the call, an unreachable empty-response check, a re-validation of a shape the schema already guaranteed, token counts nobody read, and a ten-variant error union that every consumer converted into a throw on the very next line. Transcription bypassed even that, building five provider clients inline with no timeout on four of them. We deleted the executor rather than adopting it — it was designed without reference to its callers, which is why it had none; the second instance of the pattern ADR-0014 established — and built the **AI Runtime**: one module owning all AI egress, with two entry points because Norish makes two genuinely different kinds of request, structured generation and transcription, both on one shared transport. Failures are **thrown**, as a small typed hierarchy that carries whether a retry could succeed, classified from the SDK's structured error type rather than by searching messages; the queue's enrichment runner uses that to stop burning attempts with backoff on AI having been switched off.

Where AI code lives is now a sentence rather than a dependency-graph accident: **everything under a directory named `ai/` is AI**, and it lives in `packages/shared-server` — `ai/runtime/` (the seam, its errors, provider construction), `ai/prompts/` (the loader and the nine shipped defaults), `ai/enrichment/` (the seven features whose input is a stored recipe and whose output is a domain claim, unit conversion finally beside its siblings instead of stranded where tRPC first needed it). Recipe extraction is deliberately **not** one of them: it reads raw HTML, scrapes image candidates out of it, and normalizes through the same JSON-LD normalizer as non-AI structured imports, so it is an import-pipeline feature that happens to use AI and lives with the parser in `packages/api`. A dedicated `packages/ai` was rejected for exactly that coupling — it would either drag the parser along or fail to hold extraction. Renaming `shared-server` for its newly domain-shaped contents was rejected as touching every import for a cosmetic gain; the `runtime`/`enrichment` split inside the directory already tells a reader which is which. The queue imports the six Recipe Enrichment features directly, which deleted the eight hand-copied types the handler registry kept in sync by hand; the two extraction handlers remain registered, honestly, because extraction is genuinely api-layer.

## Consequences

- A feature never constructs a provider client, never reads Generation Preferences, and never calls the SDK. A feature is a prompt, a schema, an input builder and a domain rule; its test mocks the runtime and its own data repositories, nothing else.
- Vision selection is implicit: the presence of images selects the vision model. The deleted executor carried images and a separate boolean and gated on their conjunction, so images without the flag were silently dropped — that invalid state is now unrepresentable.
- Token usage is logged by the runtime, once per request, with provider, model and feature — and is not returned, not persisted, and not exposed. Persisting it is a feature this logging is the honest prerequisite for, not a thing to sneak into a refactor.
- Retryability lives on the error, decided where the failure is understood: `AIDisabledError` and `AIConfigurationError` never retry, provider failures follow the SDK's own retryability, unusable responses always retry. A worker that catches an AI error it did not expect should let it out rather than guess.
- Transcription construction lives beside language-model construction, so the three endpoint normalizations previously duplicated between the factory and the transcriber exist once, and every transcription request runs under the existing AI timeout on the shared transport. There is deliberately no separate transcription timeout setting.
- The two transcription providers the AI SDK cannot serve — the generic OpenAI-compatible endpoint and Ollama — keep their raw clients as escape hatches _inside_ the provider boundary. Wrapping them in adapters purely to unify a return type was rejected as buying type symmetry with two shims that do nothing else.
- There are no barrels: consumers import deep paths, matching the exports maps. The deleted barrels died of having no importers; adding one back re-creates the problem ADR-0014 named.
- Adding an AI feature that bypasses the runtime — importing `generateText`, building a provider client in a feature file — is a decision to reopen this ADR, not a shortcut.
