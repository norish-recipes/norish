# Prompts are appended to, never interpolated

Six of Norish's nine AI prompts were administrator-editable; auto-categorization and allergy detection were hardcoded in source, and image extraction was worse than untunable — it took the administrator's recipe-extraction prompt and performed string surgery on it, swapping one sentence for another. By the time this was fixed, both replacement sentences had already drifted out of the shipped prompt, so the surgery had been a silent no-op telling the model it was reading a webpage while handing it photographs: the exact failure mode string surgery invites. The AI Runtime now refuses to accept a finished prompt string at all — a request names an administrator-editable **Prompt** and passes the **Prompt Sections** it wants appended, so a feature _cannot_ ship a hardcoded prompt, because there is no parameter to pass one through. Image extraction got its own prompt; the tunability gap cannot reopen.

For how a feature's input reaches the model, placeholder-based templates were rejected despite being the cleaner contract. The prompt filler silently drops a variable whose placeholder is absent, so any mechanism that adds a placeholder over time hands every self-hoster with an already-customised prompt a broken one on upgrade: their stored text predates the new placeholder, the content is silently omitted, and the damage presents as a model regression with no diagnosable cause. Appending has the strictly milder failure mode — a customised prompt keeps receiving every input block, appended after whatever text the administrator wrote. The four prompts that historically carry `{{placeholders}}` (nutrition estimation, Recipe Provenance, Ingredient Linking, unit conversion) keep them: their shipped defaults and every customised copy in the field are written against them, and their per-prompt tests pin them. The line is drawn for new content, not redrawn under existing deployments: **no prompt gains a new placeholder, and every new input arrives as an appended section.**

## Consequences

- The runtime's structured entry point takes a prompt name, sections, and — only for the four legacy prompts — fill values for the placeholders they already carry. New prompts (auto-categorization, allergy detection, image extraction) have no placeholders and never will.
- System messages stay code-owned and are not configuration. They encode invariants the code depends on: schema-parseable output, and Recipe Provenance's deliberate silence about language — a system message naming a language would override the prompt's inference from the recipe. An administrator's intent is already expressible in the Prompt, which follows the system message.
- The prompts configuration schema grows only optional fields, so stored configuration written before a prompt shipped still parses and the loader falls back to the shipped default — an upgrade is never a reason to re-do tuning.
- The administrator prompt form is table-driven: a prompt is one entry plus three translation keys, so the cost of adding one can never again be an argument for hardcoding it.
- "Return valid JSON only" was removed from system messages: structured output is enforced by the schema, and cargo instructions that restate the transport teach editors the wrong mental model.
- An end-to-end test edits a prompt through the admin surface and asserts the outgoing request carries the edited text — and that editing the recipe-extraction prompt does not change what an image import sends. Reintroducing interpolation for new content, or a second string-surgery shortcut, is a decision to reopen this ADR.
