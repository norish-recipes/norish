# Image generation is the runtime's third entry point, on its own provider

ADR-0015 gave the AI Runtime two entry points "because Norish makes two genuinely different kinds of request", structured generation and transcription. Image Generation is a third, and it is not a variation on the first: `generateImage` takes no schema, returns bytes rather than a validated object, and leaves the structured-output strategy nothing to parse. **The runtime gains `generateImage` beside `generateStructured` and `transcribe`, and Image Generation reads its own provider configuration rather than the server's.** The provider split is forced rather than chosen: of the eleven providers Norish offers, only OpenAI, Google, Azure and the OpenAI-compatible endpoints expose an image model at all — Anthropic, Mistral, DeepSeek, Groq, Perplexity and Ollama expose none — so binding image generation to the configured AI provider would put it permanently out of reach of the most common self-hosted setup in the product. The new block follows transcription's shape exactly: its own provider, model, endpoint and key, with endpoint and key falling back to the AI configuration when the provider matches, and no timeout of its own, because ADR-0015's rule that there is one AI timeout stands.

One feature, two requests. An image model is prompted, not reasoned with: a recipe's thirty ingredient lines appended to a style Prompt reliably produce a cluttered plate rather than a dish. So a job issues a structured-generation request first, turning the stored recipe into a short visual brief, and sends that brief to the image model — two administrator-editable Prompts, both appended to rather than interpolated (ADR-0016), which is why the count in the glossary moved from nine to eleven. The brief is written in English whatever language the recipe is in. It is an instruction to a model, never stored and never shown, so it is not recipe content and the care ADR-0018 takes over the language of a provenance note does not apply to it.

## Considered Options

- **One `imageModel` field beside `model` and `visionModel`.** The smallest possible change, and it makes the feature permanently unavailable to more than half the provider list, every Ollama deployment included. Rejected: a self-hoster running a local text model would have to abandon it to get a picture.
- **An OpenAI-compatible endpoint and nothing else** — one URL, one model, no provider dropdown. Covers OpenAI, Azure, LM Studio and most aggregators through a single code path, and excludes Google's Imagen and Gemini image models, which need their own transport. Rejected: Google is one of the two providers people actually reach for here.
- **One request, straight from the recipe to the image model.** Keeps the feature exactly the shape ADR-0015 describes — a prompt, an input builder and a domain rule — and spends the expensive call on a prompt nothing curated. Rejected: the cheap text call in front of it is the difference between a picture of a dish and a picture of a shopping list.

## Consequences

- Image Generation can be configured on a server whose AI provider cannot draw, and unavailable on one whose provider can, so "AI is enabled" no longer implies every kind is reachable. The coordinator gains a skip reason for an unconfigured image provider, and a manual request against one fails with it rather than reaching a worker.
- The runtime's promise narrows by one word. It still owns all AI egress, but it no longer reads one configuration: `generateStructured` reads the AI block, `transcribe` the video block, `generateImage` the image block — and only the first is what "the configured provider" means anywhere else in the product.
- A job spanning two providers can fail at either end. An unusable brief and an unusable image are both retryable; a refused image and a missing image configuration are not, and follow the existing `AIError` retryability rule rather than a new one.
- Provider capability is now a fact Norish asserts, which ADR-0014 warns against doing about model parameters. The restriction is narrower than it looks: it is a list of provider packages that expose an image model, not a claim about any model's behaviour, and a wrong entry fails at request time exactly as before.
- Adding a fourth entry point reopens this ADR, and the bar is now stated: a genuinely different kind of request, not a different feature making a kind that already exists.

## Amendment, 2026-09-19

The re-check this ADR asked for when the AI SDK line moved (to 7, for the Decision Model) found one change: `ai-sdk-ollama` 4 exposes an image model for Ollama's experimental image models, so **Ollama joined the Image Generation providers**. It takes an endpoint and no key, exactly as it does in the AI block, and borrows the AI configuration's endpoint when the provider matches. Anthropic, Mistral, DeepSeek, Groq and Perplexity still expose none, so the decision stands: the provider split is still forced, now by five providers rather than six, and "the most common self-hosted setup" can now draw without a second vendor.
