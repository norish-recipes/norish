# Image generation is the runtime's third entry point, on its own provider

ADR-0015 gives the AI Runtime one entry point per genuinely different kind of request, starting with structured generation and transcription. Image Generation is a third, and it is not a variation on the first: `generateImage` takes no schema, returns bytes rather than a validated object, and leaves the structured-output strategy nothing to parse. **The runtime has `generateImage` beside `generateStructured` and `transcribe`, and Image Generation reads its own provider configuration rather than the server's.** The provider split is forced rather than chosen: of the eleven providers Norish offers, only OpenAI, Google, Azure, Ollama (through `ai-sdk-ollama`, for its experimental image models) and the OpenAI-compatible endpoints expose an image model at all — Anthropic, Mistral, DeepSeek, Groq and Perplexity expose none — so binding image generation to the configured AI provider would put it permanently out of reach of every server whose text model comes from one of those five. The image block follows transcription's shape exactly: its own provider, model, endpoint and key, with endpoint and key falling back to the AI configuration when the provider matches (Ollama takes an endpoint and no key, as in the AI block), and no timeout of its own, because ADR-0015's rule that there is one AI timeout stands.

One feature, two requests. An image model is prompted, not reasoned with: a recipe's thirty ingredient lines appended to a style Prompt reliably produce a cluttered plate rather than a dish. So a job issues a structured-generation request first, turning the stored recipe into a short visual brief, and sends that brief to the image model — two administrator-editable Prompts, both appended to rather than interpolated (ADR-0016). The brief is written in English whatever language the recipe is in. It is an instruction to a model, never stored and never shown, so it is not recipe content and the care ADR-0018 takes over the language of a provenance note does not apply to it.

## Considered Options

- **One `imageModel` field beside `model` and `visionModel`.** The smallest possible change, and it makes the feature permanently unavailable to five of the eleven providers. Rejected: a server whose text model is Claude would have to change provider to get a picture.
- **An OpenAI-compatible endpoint and nothing else** — one URL, one model, no provider dropdown. Covers OpenAI, Azure, LM Studio and most aggregators through a single code path, and excludes Google's Imagen and Gemini image models, which need their own transport. Rejected: Google is one of the two providers people actually reach for here.
- **One request, straight from the recipe to the image model.** Keeps the feature exactly the shape ADR-0015 describes — a prompt, an input builder and a domain rule — and spends the expensive call on a prompt nothing curated. Rejected: the cheap text call in front of it is the difference between a picture of a dish and a picture of a shopping list.

## Consequences

- Image Generation can be configured on a server whose AI provider cannot draw, and unavailable on one whose provider can, so "AI is enabled" does not imply every kind is reachable. The coordinator has a skip reason for an unconfigured image provider, and a manual request against one fails with it rather than reaching a worker.
- The runtime owns all AI egress without reading one configuration: `generateStructured` reads the AI block, `transcribe` the video block, `generateImage` the image block — and only the first is what "the configured provider" means anywhere else in the product.
- A job spanning two providers can fail at either end. An unusable brief and an unusable image are both retryable; a refused image and a missing image configuration are not, and follow the `AIError` retryability rule rather than one of their own.
- Provider capability is a fact Norish asserts, which ADR-0014 warns against doing about model parameters. The restriction is narrower than it looks: it is a list of provider packages that expose an image model, re-checked whenever the AI SDK line moves, not a claim about any model's behaviour, and a wrong entry fails at request time like any other provider error.
- A further entry point has to clear the bar this ADR sets: a genuinely different kind of request, not a different feature making a kind that already exists (ADR-0035 is the fourth).
