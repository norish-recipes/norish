# Cuisines and Tags share a shape and differ in governance

Recipe Provenance needs to record a recipe's culinary style, and cuisine was already being recorded badly: ten of the predefined auto-tagging Tags are cuisines (`italian`, `mexican`, `thai`, …), minted by AI as free-form lowercase strings with no controlled vocabulary. We introduce a `cuisines` table with a `recipe_cuisines` join — structurally identical to `tags`/`recipe_tags` — and remove cuisine from the Tag vocabulary. The two pairs look like duplication and are not: **Tags are an open folksonomy** that anyone and any AI may extend at will, while **Cuisines are a curated vocabulary** that only an administrator extends, or that AI may extend only under an explicitly permissive strategy setting. Same shape, opposite write rules. We rejected a PostgreSQL enum (the upstream attempt's choice) because it cannot be extended from a settings form — extending it requires a hand-written `ALTER TYPE` migration, which is exactly the constraint administrator ownership is meant to remove. We rejected storing the vocabulary as a list in server config with a `text[]` column on recipes, because renaming a Cuisine would then silently orphan every recipe holding the old string, where a join table makes a rename one row. And we rejected simply reusing Tags, because a folksonomy cannot offer the guarantee this vocabulary exists to provide: that "Sicilian" resolves onto the row that already means Italian instead of becoming a second row meaning the same thing.

## Consequences

- Two near-identical table pairs exist by design. Neither should be "cleaned up" into the other; the difference is who may write, not how it is stored.
- The AI's output schema for cuisines is built at runtime from the current rows, not from a compile-time enum. Proposed names are always matched against the existing vocabulary before storage, under both strategies.
- `Other` is deliberately not a Cuisine. As a row it is a null-object that lets the AI avoid choosing and makes filtering meaningless; an empty Cuisine set already says "nothing in our vocabulary fits".
- The cuisine strategy is independent of the automatic-enrichment switch, following the correction already made for `tagStrategy` — how names are picked and whether the kind runs automatically are orthogonal axes.
- A one-time migration moves existing cuisine Tags onto Cuisines and removes the matched Tags — both the join rows and the now-orphaned `tags` rows. Deleting the rows is load-bearing: under the `predefined_db` tag strategy the auto-tagging prompt injects every existing tag name back in as an allowed tag, so a surviving orphan would keep cuisine in circulation after the migration meant to end it. The migration records what it removed, because that step is not reversible from within the application.
- Cuisine names are canonical identifiers, seeded in English and displayed verbatim in every locale, with no translation keys and no seeded-versus-administrator distinction at render time. The AI must therefore pick names verbatim from the supplied vocabulary whatever language it is writing prose in, or an Italian recipe yields `Italiana` and mints a second row meaning Italian.
- Tags continue to overlap the meal-time categories (`breakfast`, `lunch`, …). That is accepted and unchanged: Tags are meant to be a dumping ground, which is precisely why cuisine should not live there.
