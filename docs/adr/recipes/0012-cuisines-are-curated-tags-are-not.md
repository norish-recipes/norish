# Cuisines and Tags share a shape and differ in governance

Recipe Provenance needs to record a recipe's culinary style, and Tags record it badly: AI mints cuisines (`italian`, `mexican`, `thai`, …) as free-form lowercase Tags with no controlled vocabulary. Cuisines are a `cuisines` table with a `recipe_cuisines` join — structurally identical to `tags`/`recipe_tags` — and cuisine is not part of the Tag vocabulary. The two pairs look like duplication and are not: **Tags are an open folksonomy** that any member and AI may extend, while **Cuisines are a curated vocabulary**: the administrator's, which every household is offered, plus the ones a household adds itself (ADR-0043). AI extends it only under an explicitly permissive strategy setting, and then only the recipe's household's list. Same shape, different write rules. We rejected a PostgreSQL enum (the upstream attempt's choice) because neither an administrator nor a household could extend it — extending it requires a hand-written `ALTER TYPE` migration. We rejected storing the vocabulary as a list in server config with a `text[]` column on recipes, because renaming a Cuisine would then silently orphan every recipe holding the old string, where a join table makes a rename one row. And we rejected simply reusing Tags, because a folksonomy cannot offer the guarantee this vocabulary exists to provide: that "Sicilian" resolves onto the row that already means Italian instead of becoming a second row meaning the same thing.

## Consequences

- Two near-identical table pairs exist by design. Neither should be "cleaned up" into the other; the difference is who may write, not how it is stored.
- The AI's output schema for cuisines is built at runtime from the Cuisines the recipe's household is offered, not from a compile-time enum. Proposed names are always matched against that list before storage, under both strategies.
- `Other` is deliberately not a Cuisine. As a row it is a null-object that lets the AI avoid choosing and makes filtering meaningless; an empty Cuisine set already says "nothing in our vocabulary fits".
- The cuisine strategy is independent of the automatic-enrichment switch, as `tagStrategy` is — how names are picked and whether the kind runs automatically are orthogonal axes.
- A one-time migration moves existing cuisine Tags onto Cuisines and removes the matched Tags — both the join rows and the `tags` rows they leave unused. Deleting the rows is load-bearing: under the `predefined_db` tag strategy the auto-tagging prompt injects the existing tag names back in as allowed tags, so a surviving row would keep cuisine in circulation after the migration meant to end it. The migration records what it removed, because that step is not reversible from within the application.
- Cuisine names are canonical identifiers, the instance's seeded in English, and every Cuisine is displayed verbatim in every locale, with no translation keys and no seeded-versus-added distinction at render time. The AI must therefore pick names verbatim from the supplied vocabulary whatever language it is writing prose in, or an Italian recipe yields `Italiana` and mints a second row meaning Italian.
- Tags overlap the Categories (`breakfast`, `lunch`, …). That is accepted: Tags are meant to be a dumping ground, which is precisely why cuisine should not live there.
