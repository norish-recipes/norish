# Offline-forced is a development-only debug affordance, not a user feature

The connectivity runtime decides Live from Offline by probing the backend; for *development* we also want to force Offline on demand — to exercise the Outbox, cache-serving and Reconnect Sequence without taking a backend down — so the status modal gains a forced-Offline toggle that is **dev-only**, gated out of production by `process.env.NODE_ENV` (the same build-time strip `apps/web/lib/logger.ts` already uses) so no forced-Offline code or UI ships to users. It is modelled as an orthogonal persisted override, **not** a third state of the connectivity machine: `connectivity-machine.ts` stays a pure two-state reachability reducer (`live | offline`), and the provider derives an effective posture (`live | offline | offline-forced`) from a `localStorage` flag that in production is always absent, so the effective posture collapses back to the machine state. Because the backend is genuinely reachable when a developer forces Offline, the toggle blocks at the *transport* layer to be faithful rather than cosmetic — a posture-only flag would keep talking to the live backend and test nothing: the health probe reports unreachable, a dev-only tRPC link positioned below the Outbox link rejects every operation with an unreachable-style error (so mutations enqueue through the normal Outbox path and reads fall back to the persisted cache), the WebSocket is suspended via the bundle's `getWsLazyEnabled`/`close()` seam, and the probe loop is parked entirely (true radio silence). We rejected shipping a production, user-facing "work offline" toggle — it is not a feature Norish commits to, and an earlier draft of `CONTEXT.md` / the design record described one by mistake; this record corrects that.

## Consequences

- The modal's Offline-Toggle row renders only under `NODE_ENV !== "production"`; every other modal section (connection readout, cache status, Outbox controls, wipe-cache) ships to production.
- Exiting the toggle reuses the organic Offline→Live path: the flag clears, one probe runs, and on Live the Reconnect Sequence (drain → invalidate → warm) runs while the WebSocket un-suspends — so forced-Offline is indistinguishable from real recovery to the rest of the runtime.
- The glossary term "Offline Toggle" is redefined from a "user control" to a development affordance; "Offline (forced)" is not a product-facing connectivity state.
- Hard WebSocket suspension may need a small addition to the shared provider bundle if `getWsLazyEnabled` only governs idle-close rather than gating (re)connection — to be confirmed when built.
