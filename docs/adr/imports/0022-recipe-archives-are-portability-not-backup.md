# Recipe Archives are portability, not backup

Norish exports recipes as a Recipe Archive — a `.norishrecipes` zip holding a manifest and one folder per recipe with its media inside, read back through the same archive-import loop that reads Mela, Paprika, Mealie, Tandoor and Recipe Keeper. The feature could have been a backup: preserve ownership, carry accounts, restore an instance somewhere else. **It is an exchange of recipe content instead: importing an archive makes the importer the owner of everything it creates, and nothing about identity travels beyond display-name attribution and the exporter's own rating and favourite mark.** Emails are stored encrypted precisely so they do not leak, and an archive is a file people hand to friends, so no PII rides inside — which is also why the archive scope is simply "everything the exporter can see" under the Permission Policy, a server administrator's included, with no privileged extra data for them (ADR-0041). Cuisine names travel as words and attach only where the importing household's Cuisines (its own and the instance's) already have them, matched on the folded name: unmatched names are dropped visibly in the import result, never created — an archive would otherwise grow a curated list (ADR-0012) with whatever vocabulary its source kept — and never demoted to tags, a direction the tag→cuisine migration cleaned up once already. Provenance gaps left by dropped cuisines are Recipe Enrichment's to refill under the target instance's own rules (ADR-0018).

Cookbooks travel as titles: each recipe names every cookbook the exporter can see that holds it, and importing files the recipe into the importer's own cookbook of that title (matched case-insensitively, trimmed), making one where none exists. Cover images and cookbooks holding no exported recipe stay behind. An archive is content, not a Library: a cookbook title is something a recipe is filed under, as a foreign app's collection is, and a Recipe Keeper archive brings its collections in on the same path.

The Norish parser inherits the shared import loop's semantics — match by URL or name within household scope, overwrite on match, freshly minted IDs otherwise; archive IDs are folder keys, never reused. One archive can hold different recipes that share a name, so a name match does not win where both recipes carry a URL and the URLs differ, and a recipe the running import has already written, inserted or overwritten, is matched by URL only: an archive never overwrites its own recipes by name, while exact copies (same URL) collapse into one. The shared loop applies this to every format it reads.

Rejects: ownership-preserving restore with account matching (a different, bigger feature that would drag PII, account-matching and conflict semantics into an exchange format); auto-creating or tag-demoting unknown cuisines; a skip-on-match special case that would make Norish's own format behave unlike every other archive in the same importer; remembering only the recipes the import created, which would still let a second same-named entry overwrite the first where both matched a recipe already in the library; a manifest-level cookbook list carrying covers and empty cookbooks, a second import path only Norish would use, for a cover the receiving instance draws from the members anyway; and a background job producing server-side export artifacts — the archive streams straight to the client and never exists on the server at all.

## Consequences

- The container is effectively frozen the day archives exist in the wild — people keep export files for years. The manifest carries `formatVersion: 1` and positive format identification; evolution within a major is additive, and a future importer refuses or adapts to a newer major instead of guessing. The cookbook titles are such an addition, so an older importer ignores them.
- Importing an archive lands every recipe in it under the one importing user (or overwrites their matches), whoever owned it where it was exported. That flattening is the accepted cost; instance migration would be its own feature, and this is deliberately not it.
- Overwrite-on-match means importing a stale archive replaces edits made since it was written. Consistency with every other archive format was chosen over edit protection; protecting edits would mean changing the shared loop for all formats, not special-casing this one.
- A re-import only ever adds cookbook memberships; it never takes a recipe out of a cookbook.
- Streaming delivery means a long download for a video-heavy export. Moving to a job-built artifact later is additive and does not touch the format.
- Recipe Archive is product language and lives in `CONTEXT.md`; the container layout (manifest, per-recipe folders, relative media paths) is implementation and does not.
