# The shopping list can be an external service, reached by a one-way handoff

A household that shops with Bring! wants Norish's "add to groceries" to put the ingredients in Bring!, and Bring! gives no way to do that: there is no endpoint that takes items, only a recipe import that takes the address of a page, and Bring!'s own servers fetch that page. We chose a one-way **Bring Handoff** through a temporary unauthenticated page. For each list the server stores the lines under a 192-bit random token (24 bytes, base64url) in Valkey for one hour, serves them at a public `/share/bring/<token>` as a schema.org Recipe, and asks Bring! for the deeplink that imports that address. The page exposes a title, the servings, the item lines and the recipe's primary picture, and nothing else: no user, household, recipe id or link, and no other media. A picture the instance stores is served from a second public address, `/share/bring/<token>/image`, which never shows the recipe id; an imported picture is passed on as its own `https` address; a recipe with none gets the Norish icon. The picture lives and expires with the handoff. The record is not deleted on read, because it is unknown whether Bring! fetches once or again later; the hour (a Valkey TTL of 3600 seconds) is the only bound, apart from a handoff Bring! did not take, which is deleted at once, and one the reader left without opening Bring!, which is deleted when the panel closes. An instance Bring!'s servers cannot reach, which is one without an HTTPS `AUTH_URL` or whose address is or resolves to a private one, is refused before any request is made, and says so. The check is skipped only when `BRING_API_URL` points somewhere other than Bring!'s own address, which means a test double or a proxy stands in for it; `ALLOW_PRIVATE_ADDRESSES` plays no part, because it only seeds the page-renderer setting.

The **Shopping List Provider** is an instance setting, `builtin` or `bring`, and the switch is made in the user interface only. In Bring mode the Groceries tab and pages go and every add-to-groceries path sends to Bring!; no grocery data is deleted, the server still accepts grocery writes, the public groceries API and recurring groceries are untouched, and the offline replay of grocery mutations is untouched. Switching back is therefore lossless: the list is exactly what it was. The Pantry is consulted as before, once, when a recipe is added, because it decides which lines are sent.

The handoff is prepared when the panel opens, not when **Add to Bring!** is pressed. `bring.prepare` runs the checks, stores the lines, has Bring!'s parser read the page, asks for the deeplink and returns it with the token. Every change of ticks, servings or edited lines disables the button with a spinner and, after 300 ms without another change, rewrites the same handoff with `bring.update`, which stays on the server, asks Bring! for nothing and keeps the hour's deadline. The deeplink does not change on an update: it names only the page, which Bring! reads when the link is opened, and the quantities sent are equal (`baseQuantity` and `requestedQuantity`), so the servings do not alter it. The button is enabled once the handoff holds the current list, and the press only opens the deeplink, synchronously, with the platform's `openExternalUrl`. On the web that is `window.open` in a new tab with the opener cut by hand, except in an iOS Home Screen app, where it is `location.assign`, because a new window there is an in-app browser that never hands the link to the app. It answers false when the browser blocked the tab, and only then is there a persistent toast with **Open Bring!**. On the phone `openExternalUrl` hands the link to the operating system and answers true. A failed prepare shows the reason as a toast, and the next press tries again. The server records who prepared a handoff (never shown on the page); only that person may update or discard it. Closing the panel without opening Bring! deletes the handoff with `bring.discard`; one that was opened stays up to its hour. "Add at once" after planning opens the panel when the list is Bring!, because it cannot open Bring! without a press. None of the three procedures is queued offline: a replayed one would point at a page that expired while the phone was out of signal.

The trade-off is deliberate: the household's list now lives where Norish cannot see it. Nothing is read back, nothing is kept in step, and Norish's prices, aisles and shared ticking do not apply to Bring!'s list. The instance must also be reachable from the internet, which a LAN-only install is not.

Rejected: **blocking grocery writes** while Bring! is chosen, which would break the public API, recurring groceries and offline replay for a setting that only changes where new ingredients go, and make switching back lossy or an error; **a database table** for handoffs, which needs a migration and a sweeper for a record that is worth an hour; **exposing the real recipe share link**, which would publish the recipe, its media and its author to a third party and ties the list to a recipe someone may later unshare; **reusing Norish's own recipe share link**, which cannot be recovered because the server keeps only a hash of a share token, whose page carries no schema.org Recipe, which would send the whole recipe and not the picked, scaled, Pantry-filtered lines, and which would bypass the share permission and publish steps and expose notes and every photo; **opening the link after the server answers**, as a press that sends and then opens did at first, which fails on an iPhone Home Screen web app: iOS hands a universal link to a native app only when it is opened straight from a tap, not after a wait on the server, so Bring! never opened; **preparing on open but letting the press push the last change**, which makes the press wait again and races with Bring!'s read of the page; and **a blank tab opened in the press** and sent to the link later, which a prepared handoff makes unnecessary.

## Consequences

- The setting is the `grocery_list_provider` configuration key, announced on change like the other general settings; every client reads it, and the server rereads it in `bring.prepare` and `bring.update`, so a stale client cannot send on an instance that switched back.
- A handoff record is `{title, servings, lines, image, createdAt}`, where `image` is `{recipeId, file}` for a stored picture, `{url}` for an imported one or null, plus the id of the user who prepared it, which only `update` and `discard` compare and the page never shows. Neither the token nor the page address is logged. Only an `https` imported address is passed on; the image route answers 404 for anything else, with `Cache-Control: private, no-store`.
- A person may prepare thirty handoffs in ten minutes; further prepares return `rate-limited`. A prepare is counted only once it has passed the provider, recipe-access and reachability checks, so a refusal that costs nothing does not use up the quota. An update is not counted, since it makes no request to Bring!. A handoff whose deeplink Bring! did not give is deleted at once.
- Bring! thereby also sees the instance's public address, and anyone holding the temporary link can read the lines and see the recipe's primary picture until it expires after an hour.
- A reverse proxy must let `/share/bring/` through, the page and `/image`, without login, VPN or bot protection; one that already lets `/share/` through covers it.
- Asking for the deeplink does not prove that Bring! can read the page: Bring! fetches it only when the link is opened, through its recipe parser (`GET /rest/bringrecipes/parser?url=`), and a failure there shows only Bring!'s own "not a valid recipe". So the server calls that parser itself, in `bring.prepare`, before it asks for the deeplink. When the parser could not fetch the page the prepare answers `page-unreachable` with the HTTP status the instance gave it, which names a reverse proxy, login or bot check standing in front of `/share/bring/`; when it fetched the page and found no recipe, `bring-rejected`; the toast names the status.
- Only an `https` deeplink is accepted from Bring!'s own API (`http` only from a configured `BRING_API_URL`), and both apps' `openExternalUrl` refuse any scheme but `http` and `https`, and answer whether the link was opened.
- Lines are sent with the unit written short in the reader's language, as the interface writes it (`250 g flour`, not the stored `gram`), because Bring! parses that best; an item with no usable name is left out and a send carries at most 150 lines.
- Expected failures are returned as a reason (`not-bring`, `not-public`, `page-unreachable`, `bring-unreachable`, `bring-rejected`, `rate-limited`), not thrown, so each has its own message.
- `BRING_API_URL` exists only so a test can stand in for Bring!; the default is Bring!'s own address, and Bring!'s deeplink and parser endpoints are undocumented, so `bring-client.ts` is the one place that knows their shape.
- The mobile app ignores the setting in this release. Its platform adapter says `supportsExternalShoppingList: false`, and the shared `useGroceryListProvider` then answers `builtin` without asking the instance, so the groceries tab, the add screens and the pantry keep the built-in list and its wording exactly as before. The gate is lifted when the app hides its tab, redirects its groceries stack and relabels its add screens.
- A later external provider is a new value of the setting and its own handoff, not a generalisation of this one.
